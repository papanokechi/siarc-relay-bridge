## Which route to use

**Route A (preferred) — two in-place edits.** Non-destructive: every `<em>`,
`<sub>`, `<sup>` and HTML entity in the retained abstract stays exactly as
published, because you never touch those paragraphs.

**Route B — full replacement.** Only if the description editor offers an HTML
**source / code view**. Do **not** paste the HTML below into the rich-text box
directly: it would render as literal `<p>` tags. And do not paste a plain-text
version — the abstract contains ~40 entities and inline tags (`<em>V</em><sub>quad</sub>`,
`&asymp;`, `&Prime;`, `&radic;`, `D<sub>5</sub><sup>(1)</sup>`), and a plain
paste would destroy all of them **while still passing the verifier**, since the
verifier strips tags before comparing. That is a silent failure mode; Route A
does not have it.

## A defect this found, before the edit rather than after

The verifier's invariant *"abstract retained unedited: both C1 sentences still
present"* counted **paragraphs** containing either refuted phrase and required
exactly 2. But Edit 2 quotes **both** phrases back, by design — so a correct edit
would have produced 3 and the check would have reported **8 of 9**. The natural
reading of that would have been "the paste went wrong", and the natural repair
would have been to weaken a check that was in fact working.

Fixed by excluding the boundary paragraph from the count, which is principled:
the boundary paragraph quotes the sentences deliberately, the abstract contains
them because it is retained. The check still requires exactly 2 — it was not
loosened. If it ever reports 1, the abstract really was edited and that is a halt
condition.

Same class as the whitespace caveat in `NEXT-STEPS.md`, and the reason to run a
checker against a simulated pass before trusting a real one.
